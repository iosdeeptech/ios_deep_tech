Task Local изнутри. Как читать исходники рантайма Swift

Как с ассистентом в роли проводника дойти от @TaskLocal до C++ рантайма на теге своего компилятора и подтвердить устройство хранилища task-local тестом и замером.

#swift#concurrency#task-local#runtime#ai

В 1. Task Local мы разбирали, как объявить task-local значение и привязать его через withValue. В прошлой статье четвёртый шаг работы с ассистентом предлагал попросить ссылку на proposal, документацию или строку исходников на теге и прочитать источник самим. Здесь вы возьмёте строку исходников и пройдёте этот шаг целиком на одном механизме, от макроса @TaskLocal до функций рантайма на C++.

Объяснений task-local много, и они расходятся. SE-0311 пишет, что операция async {} (сегодня Task {}) получает копию всех привязок. В сессии WWDC23 о structured concurrency говорят, что рантайм держит прямую ссылку на задачу с нужным ключом. Популярные статьи, например в Hacking with Swift, объясняют, что Task.detached не наследует значения, потому что у неё нет родителя, хотя родителя нет и у Task {}. Какое из этих объяснений верно для компилятора из вашего Xcode и как убедиться в этом самим?

После статьи вы сможете:

  • по выводу xcrun swiftc --version найти тег исходников своего компилятора и сказать, какой код пришёл из SDK, а какой из рантайма ОС;
  • пройти от @TaskLocal через @_silgen_name, Builtins.def и GenBuiltin.cpp до функций рантайма на C++ и убедиться, что нужная ветка #if собирается для вашей платформы;
  • нарисовать список task-local значений задачи после каждого withValue и объяснить, что получают async let, addTask, Task {} и Task.detached;
  • поставить замер, который отличает односвязный список от хеш-таблицы, записав прогноз до запуска;
  • запустить тест из test/Concurrency/Runtime без сборки компилятора и прочитать его строки REQUIRES и CHECK.
!

Нужно знать, как объявить task-local и чем Task отличается от Task.detached. Перед чтением полезно освежить API из 1. Task Local, 2. Task(Detached) - техническое определение, 2. Task Group и пять шагов работы с ассистентом. Писать на C++ не придётся, но читать будем: указатели, цикл по списку и std::set.

Для Apple Swift version 6.3.1 тег в репозитории swiftlang/swift называется swift-6.3.1-RELEASE. Ссылки и номера строк в статье даны по этому тегу и по swift-6.4.0-RELEASE, а не по main. Все примеры собраны Swift 6.3.1 из Xcode 26.4.1 в режиме Swift 6 и запущены на Mac mini с Apple M4 и macOS 26.3.1. Программы, чей вывод зависит от порядка работы задач, и программы из ловушек мы запускали от 10 до 200 раз, и их вывод не менялся.

Кроме компилятора, версию кода в программе задают SDK и ОС. Тела функций стандартной библиотеки с @_alwaysEmitIntoClient, а в сборке с -O обычно и с @inlinable, компилятор берёт из .swiftinterface в SDK и встраивает в приложение. Вторая строка этого файла называет компилятор, которым он создан:

От @TaskLocal до C++

Флаг -dump-macro-expansions (через -Xfrontend) показывает, что для enum RequestContext { @TaskLocal static var userID: Int = 0 } макрос создаёт свойство только для чтения get { $userID.get() } и static let $userID: TaskLocal<Int> = TaskLocal(wrappedValue: 0). Адрес объекта TaskLocal в $userID и служит ключом в рантайме:

@_silgen_name задаёт имя символа. Если у функции нет тела, как у _taskLocalValueGet, тело написано на C++ в рантайме, и его ищем в .cpp той же папки по имени с суффиксом Impl. Так находится swift_task_localValueGetImpl в TaskLocal.cpp (строки 109-128). Пара с Impl есть не у всех функций рантайма, поэтому, если поиск с суффиксом ничего не дал, ищите имя целиком. Такой переход удобно поручить ассистенту, назвав тег в вопросе: «Где на теге swift-6.3.1-RELEASE определена swift_task_localValueGet? Дай путь, функцию и строку».

Привязка идёт через встроенную функцию компилятора Builtin.addTaskLocalValue, у которой нет исходника на Swift. Её запись BUILTIN_MISC_OPERATION(AddTaskLocalValue, "addTaskLocalValue", ...) лежит в include/swift/AST/Builtins.def (строка 1222). Второй аргумент записи это имя из Swift, а первый называет элемент BuiltinValueKind. По нему в lib/IRGen/GenBuiltin.cpp находится case (строки 1586-1592), который через emitBuiltinTaskLocalValuePush превращает встроенную функцию в вызов swift_task_localValuePush с ключом, значением и метаданными типа значения. В .swiftinterface SDK, как и на теге swift-6.3-RELEASE, тело withValue вызывает Builtin.taskLocalValuePush, которую обрабатывает тот же case. Оба пути целиком:

Всё хранилище task-local значений задачи состоит из одного поля head, указателя на первый элемент односвязного списка. Поле лежит в приватной части задачи (TaskLocal::Storage Local в TaskPrivate.h, строка 812).

Вид элемента хранится в младших битах указателя на следующий элемент. Элементы выровнены по 8 байт, три младших бита их адреса всегда нулевые, и llvm::PointerIntPair<Item *, 2, Kind> кладёт два бита вида в биты 1 и 2. Видов четыре:

ВидКто создаётЧто значит
ValuewithValueобычная привязка: ключ, метаданные типа и само значение
ValueInTaskGroupBodywithValue в теле withTaskGroupдочерняя задача группы обязана такую привязку скопировать
ParentTaskMarkerсоздание дочерней задачисобственные элементы задачи кончились, next указывает в список предка
StopLookupMarkerизолированный deinit (SE-0371)всё, что ниже, при поиске не видно

У элемента-значения после nextAndKind идут два поля: key с адресом объекта TaskLocal и valueType с метаданными типа значения (TaskLocal.h, строки 97-100). Само значение лежит сразу за ними.

OpaqueValue* TaskLocal::Storage::getValue(AsyncTask *task,
                                          const HeapObject *key) {
  assert(key && "TaskLocal key must not be null.");


  auto item = head;
  while (item) {
    if (auto valueItem = dyn_cast<ValueItem>(item)) {
      if (valueItem->key == key) {
        return valueItem->getStoragePtr();
      }
    } else if (item->getKind() == Item::Kind::StopLookupMarker) {
      break;
    }


    item = item->getNext();
  }


  return nullptr;
}

ValueItem::create записывает в next нового элемента текущую голову (строки 266-267) и берёт память из аллокатора задачи, а без задачи из malloc (строки 269-271). popValue сдвигает голову и уничтожает старый элемент. В элемент попадает копия значения, которую делает сам withValue (комментарий в TaskLocal.swift, строки 243-248), и для класса это retain, который держит объект до конца области.

Поиск идёт от головы к первому элементу с тем же ключом. dyn_cast<ValueItem> подходит обоим видам значений, а маркер родителя не обрабатывается, и обход продолжается по элементам предка. Остановить поиск могут только StopLookupMarker и конец списка, и тогда get() отдаёт значение по умолчанию из самого объекта TaskLocal (TaskLocal.swift, строки 164-168 и 181-183).

Отсюда цена чтения. Она растёт с числом элементов до первого совпадения, а ключ, который нигде не привязан, проходит весь видимый список.

Без задачи, когда swift_task_getCurrent() возвращает nullptr, такое же хранилище живёт в thread-local переменной потока (TaskLocal.cpp, строки 94-106 и 137-145).

Чтобы увидеть список в памяти, мы написали отладочную функцию dump. Она идёт по нему, как getValue, и печатает вид и адрес каждого элемента. Смещение head в памяти задачи находит findHeadOffset: она привязывает служебный ключ Probe.$marker и ищет слово, которое стало указателем на его элемент.

SWIFTListDump.swift
func currentTask() -> UnsafeRawPointer? {
  withUnsafeCurrentTask { task in task.map { unsafeBitCast($0, to: UnsafeRawPointer.self) } }
}
// ...
func findHeadOffset() async -> Int {
  await Task.detached { () -> Int in
    let task = currentTask()!
    let before = (0..<48).map { task.load(fromByteOffset: $0 * 8, as: UInt.self) }
    return Probe.$marker.withValue(0x5EED) { () -> Int in
      for i in 0..<48 where before[i] == 0 {
        let word = task.load(fromByteOffset: i * 8, as: UInt.self)
        guard word > 0x1_0000_0000, word % 8 == 0, let item = UnsafeRawPointer(bitPattern: word) else { continue }
        if item.load(fromByteOffset: 8, as: UInt.self) == address(Probe.$marker),
           item.load(fromByteOffset: 24, as: Int.self) == 0x5EED {
          return i * 8
        }
      }
      return -1
    }
  }.value
}
// ...
func dump(_ label: String) {
  guard let task = currentTask() else { return }
  var item = task.load(fromByteOffset: headOffset, as: UInt.self)
  print("== \(label)")
  while item != 0 {
    let p = UnsafeRawPointer(bitPattern: item)!
    let word0 = p.load(as: UInt.self)
    let kind = Int((word0 >> 1) & 3)   // вид в битах 1-2
    var text = kinds[kind]
    // ...
    print("   \(text)  [биты вида: \(word0 & 7), адрес: 0x\(String(item, radix: 16))]")
    item = word0 & ~UInt(7)               // следующий элемент
  }
  print("   конец списка")
}

Что получает новая задача

Дочерними мы, как и рантайм, называем только задачи async let и группы, у которых при создании стоит флаг isChildTask. Task {} документация стандартной библиотеки называет неструктурированной задачей верхнего уровня (Task+init.swift.gyb, строка 246).

Кроме привязок в теле группы (о них ниже), дочерняя задача ничего не копирует. Рантайм создаёт в её памяти один ParentTaskMarker и направляет его на текущую голову списка родителя. Так можно, потому что дочерняя задача гарантированно завершается раньше, чем родитель снимет свои элементы (комментарий в TaskLocal.h, строки 184-190). В выводе dump у async let первым идёт маркер с битами 4 (вид 2, сдвинутый на один бит), за ним три элемента родителя с теми же адресами.

Из этого же следует требование Value: Sendable в объявлении TaskLocal (TaskLocal.swift, строка 163), ведь дочерние задачи читают одно и то же значение из памяти родителя, иногда одновременно (SE-0311, раздел «Reading task-local values»).

Если у родителя есть только собственный маркер, дочерняя задача перешагивает через него к ближайшему предку со значениями (строки 229-235). SE-0311 описывает эту оптимизацию в разделе «Reading task-local values: implementation details», а в сессии WWDC23 её называют прямой ссылкой на задачу с нужным ключом. В коде маркер указывает на голову списка предка, и ключ дальше ищется обычным обходом.

Task {} копирует последнюю привязку каждого ключа

copyTo идёт от головы списка через маркеры родителей и копирует первое встреченное, то есть самое свежее, значение каждого ключа, а скопированные ключи запоминает в std::set. Каждая копия встаёт в голову списка новой задачи (ValueItem::copyTo, строки 275-286), поэтому в выводе dump у Task {} сначала идёт debugMode, а за ним userID=2. Адреса у копий новые, а userID=1 в список не попал.

Комментарий к copyTo в TaskLocal.h (строки 217-226), как и SE-0311, говорит о копии всех привязок и уточняет, что ради оптимизации копируется только последняя привязка ключа. Копию делает vw_initializeWithCopy (TaskLocal.cpp, строка 280), и для класса это ещё одна сильная ссылка. Чтением копию всех привязок от копии последней не отличить, ведь поиск всё равно находит последнюю. Их различает время жизни объектов:

У Task.detached список пуст

Для Task.detached рантайм не вызывает ни initializeLinkParent, ни copyTo. Для task-local значений от Task {}, у которой родителя тоже нет, её отличает только флаг copyTaskLocals.

Привязка в теле группы

SE-0311 описывает withValue прямо вокруг group.addTask как ошибку, которая роняет программу, потому что группа живёт дольше области withValue и дочерняя задача могла бы прочитать снятый элемент. Рантайм Swift 6.0 (iOS 18 и macOS 15, utils/availability-macros.def, строка 46) такие привязки вместо этого копирует (PR #73978). На теге 6.3.1 pushValue помечает элемент видом ValueInTaskGroupBody, если у задачи есть запись группы (TaskLocal.cpp, строка 438), а initializeLinkParent копирует в дочернюю задачу подряд идущие элементы этого вида из головы списка родителя (строки 213-227).

Вторая часть ListDump.swift работает с группой. Внутри withTaskGroup идут три вложенные привязки (userID=30, debugMode=true, userID=31) поверх userID=10, привязанного до группы, а addTask с вызовом dump стоит в самой внутренней области. Вывод такой:

Дочерняя задача скопировала userID=31 и debugMode, пропустила более старую привязку userID=30 и маркером сослалась на userID=10 родителя, адрес у него тот же. Копия принадлежит самой дочерней задаче, поэтому значение остаётся у неё и после того, как родитель снимет привязку. Копирование делает рантайм ОС, а не компилятор, поэтому результат зависит от версии ОС на устройстве. SE-0311 советует привязывать значение вокруг всей группы или внутри замыкания addTask. Тогда у привязывающей задачи нет записи группы (если она сама не в теле другой группы), элемент получает вид Value, и рантайм ничего не копирует.

!Если приложение поддерживает iOS 17›

В рантайме 5.10 (iOS 17.4 и macOS 14.4) вида ValueInTaskGroupBody нет, и привязка в теле группы не копируется. На теге 5.10 заголовок TaskLocal.h лежит в include/swift/ABI/. С -Onone синхронный withValue берётся из библиотеки ОС и на iOS 17 падает на проверке _checkIllegalTaskLocalBindingWithinWithTaskGroup (TaskLocal.swift на теге swift-5.10-RELEASE, строки 193-204). С -O синхронный withValue встраивается из SDK, а асинхронный помечен @backDeployed(before: SwiftStdlib 6.0) (TaskLocal.swift на 6.3.1, строка 206), и до iOS 18 работает его копия из SDK. В коде из SDK этой проверки нет, и дочерняя задача ссылается на элемент, который родитель освободит при выходе из withValue. Поэтому на iOS 17 держитесь совета SE-0311 выше. Это вывод по исходникам и по nm -u программы с withValue вокруг addTask в теле группы, собранной с -target arm64-apple-macos14.0 -Onone. Ни на iOS 17, ни на macOS 14 мы её не запускали.

Тесты как исполняемая спецификация

Большинство тестов из test/Concurrency/Runtime сравнивают вывод программы со строками // CHECK: в том же файле, а тесты компилятора вроде task_local.swift сверяют диагностики с комментариями expected-error.

На теге 6.3.1 в test/Concurrency/Runtime 11 файлов с task_local в имени. Прежде чем опираться на тест, посмотрите на его строки REQUIRES. Два теста копирования в Task {} (async_task_locals_copy_to_async.swift и async_task_locals_copy_to_sync.swift) требуют возможность rdar80824152, которую конфигурация тестов на этом теге нигде не объявляет, поэтому по правилам lit они не запускаются. Ни один из 11 тестов не проверяет, что отсоединённая задача ничего не наследует. Это правило записано в коде (taskIsDetached в Task.cpp, строки 677-679) и в документации TaskLocal.swift (строки 86-88).

Чтобы запустить тест, компилятор собирать не нужно. Начните со строки RUN:

SWIFTtest/Concurrency/Runtime/async_task_locals_basic.swift, swift-6.3.1-RELEASE, строка 1
// RUN: %target-run-simple-swift( -plugin-path %swift-plugin-dir -parse-as-library %import-libdispatch) | %FileCheck %s

%target-run-simple-swift( флаги ) значит собрать файл с этими флагами и запустить, а | %FileCheck %s значит сравнить вывод со строками CHECK этого файла. Вручную к сборке добавляют -module-name main, как делает конфигурация lit (test/lit.cfg), и задают макросы доступности SwiftStdlib 5.1 и 5.10 флагом -define-availability со значениями из utils/availability-macros.def того же тега:

Командой выше мы собрали и запустили 9 из 11 тестов тега 6.3.1, включая два выключенных. Два оставшихся, тесты изолированного deinit, требуют библиотеку StdlibUnittest, которой в Xcode нет. Утилиты FileCheck в Xcode тоже нет, поэтому мы сравнивали вывод небольшим скриптом по её правилам. У каждого из девяти тестов вывод совпал со всеми строками CHECK.

*Как сравнить вывод без FileCheck›

Строки // CHECK: должны встретиться в выводе по порядку, в любом месте строки, CHECK-NEXT на следующей строке после предыдущего совпадения, {{...}} означает регулярное выражение, а [[X:...]] запоминает найденное. Для одного теста хватает grep -n CHECK async_task_locals_basic.swift и сравнения с выводом ./basic на глаз.

Ассистент как проводник по репозиторию

Путь от @TaskLocal до getValue состоит из коротких переходов: имя в Swift, строка @_silgen_name, функция с суффиксом Impl, метод задачи, структура в заголовке, тест. На каждом переходе можно спросить ассистента, в каком файле, функции и строке на нужном теге искать дальше. Пять шагов из прошлой статьи на примере task-local выглядят так:

ШагЧто делаете на примере task-local

Что изменилось в Swift 6.4.0

Swift 6.4.0 уже вышел, но в Xcode 26.4.1 его нет. Всё в этом разделе взято из исходников и тестов на теге swift-6.4.0-RELEASE, а компилятором 6.4.0 мы ничего не запускали.

Хранилище не изменилось. TaskLocal.h совпадает с 6.3.1 байт в байт, а в TaskLocal.cpp одна новая пара #if вокруг отчёта для отладчика сдвинула функции ниже на две строки. Изменились Swift-слой, макрос и генератор кода:

  • get() стал @_alwaysEmitIntoClient, и его тело всегда попадает в код приложения (PR #88334). Для непривязанного ключа он вызывает __abi_get(), под которым остался прежний символ get(), и тот проходит список ещё раз (TaskLocal.swift, строки 184-186 и 209-210).
  • Появилась перегрузка nonisolated(nonsending) func withValue (PR #89061), где изоляцию вызывающего задаёт сам тип функции, а не параметр isolation: isolated (any Actor)? = #isolation, как у прежней перегрузки. Прежнюю пометили deprecated (TaskLocal.swift, строка 264).
  • Макрос добавляет к $name слово nonisolated (TaskLocalMacro.swift, строки 109 и 114), и тест async_task_locals_basic_warnings.swift с -default-isolation MainActor (строки 7-9) объявляет @TaskLocal nonisolated static var number (строка 35), что на 6.3.1 в этом режиме не собирается (ловушка ниже).
  • В GenBuiltin.cpp исправлено падение при значении-замыкании в релизной сборке (коммит 7118b18).

Ловушки

Чтение в горячем цикле

Каждое обращение к RequestContext.userID проходит список до нужного ключа и возвращает копию значения (TaskLocal.swift, строка 188 на 6.3.1), а для класса копия означает retain. В горячем цикле прочитайте значение один раз до цикла и работайте с локальной константой, как советует SE-0311.

Колбэк на очереди GCD

Если внутри задачи вызвать старый API с колбэком, колбэк выполнится на потоке GCD и привязку задачи не увидит:

SWIFTCallback.swift
// Колбэк на очереди GCD и task-local значение задачи
import Dispatch


enum RequestContext {
  @TaskLocal static var requestID: String?
}


func log(_ message: String) {
  print("[\(RequestContext.requestID ?? "nil")] \(message)")
}


/// Старый API с колбэком на глобальной очереди
func loadAvatar(completion: @escaping @Sendable () -> Void) {
  DispatchQueue.global().async { completion() }
}
// ...
    await RequestContext.$requestID.withValue("req-42") {
      log("в задаче")
      await withCheckedContinuation { done in
        loadAvatar {
          log("в колбэке")
          done.resume()
        }
      }
      let requestID = RequestContext.requestID  // читаем в задаче
      await withCheckedContinuation { done in
        loadAvatar {
          RequestContext.$requestID.withValue(requestID) {  // и привязываем заново
            log("в колбэке после новой привязки")
          }
          done.resume()
        }
      }
    }
TEXT
[req-42] в задаче
[nil] в колбэке
[req-42] в колбэке после новой привязки

Колбэк DispatchQueue.global().async выполняется вне задачи, и рантайм ищет значение в thread-local хранилище потока (TaskLocal.cpp, строки 118-127), где ничего не привязано. Прочитайте значение в задаче, захватите его в колбэк и привяжите заново, как во второй половине программы.

Замыкание как значение в релизной сборке Swift 6.3.1

SWIFTClosureValue.swift
// Task-local со значением-замыканием
@TaskLocal var onLog: (@Sendable () -> Void)?


@main
struct ClosureValue {
  static func main() {
    $onLog.withValue({ print("log") }) {
      onLog?()
    }
    print("done")
  }
}

С -Onone программа печатает log и done, а с -O падает с кодом 139 (SIGSEGV), ничего не напечатав. Причина в GenBuiltin.cpp (строки 1586-1592 на 6.3.1). Для функционального типа компилятор передаёт там в swift_task_localValuePush метаданные пониженного типа вместо настоящего, и программа падает внутри swift_task_localValuePushImpl.

Падение видно только с -O, потому что синхронный withValue объявлен @inlinable и только тогда его тело встраивается в приложение, которое само вызывает swift_task_localValuePush. С -Onone приложение вызывает обобщённый withValue из библиотеки ОС. nm -u у такой сборки показывает Swift.TaskLocal.withValue<A>(…), а с -O вместо него _swift_task_localValuePush. На теге 6.4.0 ошибка исправлена, а на 6.3.1 помогает обёртка в структуру, с ней сборка с -O работает:

SWIFTClosureWrapped.swift
// То же замыкание, завёрнутое в структуру
struct LogHandler: Sendable {
  let call: @Sendable () -> Void
}


@TaskLocal var onLog: LogHandler?
// ...
    $onLog.withValue(LogHandler { print("log") }) {
      onLog?.call()
    }

Изоляция MainActor по умолчанию

Шаблон приложения в Xcode 26.4.1 ставит SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor, и тип с @TaskLocal целиком изолирован на главном акторе. Тогда Swift 6.3.1 не даёт читать значение без await из Task.detached, addTask или синхронной nonisolated функции. Программа из задачи «Что будет выведено?» ниже в таком модуле не собирается, компилятор отвечает main actor-isolated static property 'spanID' cannot be accessed from outside of the actor. Пометка nonisolated у самого свойства не помогает, потому что сгенерированное макросом свойство с $ остаётся изолированным. Собирается вариант с nonisolated на всём типе, например nonisolated enum Trace. Программы статьи собраны через xcrun swiftc без этого режима.

Task-local вместо параметра

SE-0311 просит не заменять обычные параметры task-local значениями (разделы «Binding values for the duration of a child-task» и «Intended use-cases»). Task-local подходит для метаданных вроде идентификатора трассировки, которые не меняют результат функции. Если без привязанного значения функция работает неправильно, передавайте его параметром.

Вопросы на собеседовании

Ответьте сами, прежде чем раскрыть подсказку.

?Где хранятся task-local значения задачи и сколько стоит чтение?›

В односвязном списке, на который указывает поле head задачи. Чтение идёт от головы до первого элемента с ключом, и в горячем цикле на Apple M4 стоит около 4 нс для ключа в голове и около 200 нс под 128 привязками.

?Что получают async let, addTask, Task и Task.detached?›

async let и addTask получают ParentTaskMarker на голову списка родителя и, кроме привязок в теле withTaskGroup, ничего не копируют, потому что дочерняя задача завершится раньше, чем родитель снимет привязки. Task {} и Task.immediate получают копию последней привязки каждого ключа, а Task.detached без флага copyTaskLocals не получает ничего.

?Что будет выведено?›
SWIFT
enum Trace {
  @TaskLocal static var spanID: String = "none"
}


@main
struct Puzzle {
  static func main() async {
    await Trace.$spanID.withValue("a") {
      await Trace.$spanID.withValue("b") {
        async let child = Trace.spanID
        let copy = Task { Trace.spanID }
        let clean = Task.detached { Trace.spanID }
        print(await child, await copy.value, await clean.value)
      }
    }
    let fromGroup = await withTaskGroup(of: String.self) { group in
      Trace.$spanID.withValue("c") {
        group.addTask {
          try? await Task.sleep(for: .milliseconds(50))
          return Trace.spanID
        }
      }
      return await group.next()!
    }
    print(fromGroup, Trace.spanID)
  }
}
TEXT
b b none
c none

async let читает голову списка родителя, где лежит b. Task {} получила копию последней привязки, тоже b. Task.detached видит значение по умолчанию. Во второй строке дочерняя задача группы читает значение через 50 мс, когда область withValue("c") уже закрыта, и видит c, потому что привязка в теле группы скопирована в неё рантаймом Swift 6.0 и новее.

?Почему значение нельзя присвоить, а только привязать через withValue?›

Привязка снимается сама при выходе из области, и никакой код не может забыть её снять. Автор SE-0311 в первом ревью назвал это главной целью и от неструктурированного set отказался сознательно. Из-за областей родитель только кладёт элементы в голову списка и снимает их, а элементы, которые видит дочерняя задача, снимает лишь после её завершения (комментарий в TaskLocal.h, строки 173-190). Поэтому дочерние задачи читают его список без блокировок.

?Как вы разбираетесь в незнакомом коде рантайма вместе с ассистентом?›

Хороший ответ называет порядок: тег компилятора и записанный прогноз, запрос к ассистенту на файл, функцию и строку на этом теге, чтение функции целиком, затем тест или своя программа, которая различает гипотезы. Добавьте пример: путь по @_silgen_name и суффиксу Impl до Storage::getValue и замер, который подтвердил список.

Итог

  • У задачи один указатель head на односвязный список привязок, и цена чтения растёт с позицией привязки.
  • async let и addTask получают маркер на список родителя, Task {} копирует последнюю привязку каждого ключа, Task.detached не получает ничего.
  • Начиная с рантайма Swift 6.0 (iOS 18, macOS 15), привязка в теле withTaskGroup вокруг addTask копируется в дочернюю задачу.
  • Имя тега исходников следует из вывода xcrun swiftc --version. Встраиваемый код приходит из .swiftinterface SDK, C++ рантайм из ОС, и на Mac его версию показывает dyld_info.
  • От Swift до C++ ведут @_silgen_name и суффикс Impl, от Builtin.* ведут Builtins.def и GenBuiltin.cpp. Перед ссылкой на строку проверьте ветку #if, а у теста строки REQUIRES.
  • В Swift 6.4.0 хранилище то же, а тело get() попадает в код приложения.

Практика

Первую задачу решайте сами, две другие вместе с ассистентом по пяти шагам.

1. Предскажите вывод программы и объясните его по строкам TaskLocal.cpp.

SWIFTLateChild.swift
// async let создан при req-1 и читает значение, когда родитель уже внутри req-2
enum RequestContext {
  @TaskLocal static var requestID: String?
}


func current() -> String { RequestContext.requestID ?? "nil" }


@main
struct LateChild {
  static func main() async {
    await RequestContext.$requestID.withValue("req-1") {
      let (childGate, openChild) = AsyncStream<Void>.makeStream()
      let (readDone, markRead) = AsyncStream<Void>.makeStream()
      async let late: String = {
        for await _ in childGate { break }  // ждём, пока родитель войдёт в req-2
        let seen = current()
        markRead.yield()
        return seen
      }()
      await RequestContext.$requestID.withValue("req-2") {
        print("родитель:", current())
        openChild.yield()
        for await _ in readDone { break }    // дочерняя задача прочитала значение
      }
      print("async let:", await late)
    }
  }
}

async let: req-1

При создании async let рантайм записывает в маркер текущую голову списка родителя (auto item = parent->_private().Local.head, строка 178; tail->setNext(item), строка 247). Привязка req-2 ложится в голову списка родителя, выше элемента, на который смотрит маркер, и обход дочерней задачи до неё не доходит.

✓Где искать (swift-6.3.1-RELEASE)›

Task.isCancelled (TaskCancellation.swift, строки 143-147) берёт UnsafeCurrentTask.isCancelled (Task.swift, строки 750-752), а тот вызывает _taskIsCancelled с @_silgen_name("swift_task_isCancelled") (строки 913-915). Функция определена в Task.cpp без суффикса Impl (строка 1748) и через AsyncTask::isCancelled() (TaskPrivate.h, строки 968-971) проверяет флаг IsCancelled = 0x100 (строка 442) в атомарном слове статуса задачи. Списка task-local в цепочке нет, и SE-0311 в разделе «Task Local Values» оговаривает, что отмена и приоритет хранятся иначе.
