Observation вместо ObservableObject

Переносим экран заказов с ObservableObject на @Observable и проверяем, какие свойства заставляют SwiftUI пересчитывать body. Разбираем @State, @Bindable, Environment и Observations.

#swift#swiftui#observation

На экране заказа изменился статус, а SwiftUI снова вызвал body у блока с суммой. Сама сумма осталась прежней. Такой вызов не означает, что на экране что-то обязательно изменится, но лишнюю работу представление уже выполнило.

В 2. Property Wrappers мы использовали ObservableObject, @Published, @StateObject и @ObservedObject. Перенесём знакомую модель на Observation и оставим прежний экран. Затем изменим только статус и посчитаем вызовы body у двух блоков.

!

Нужно знать. Пригодятся свойства классов и вычисляемые свойства Swift, а также View, body, @State и Binding из 1. Основы и 2. Property Wrappers.

Модель до перехода

Возьмём два свойства заказа: текст статуса и отформатированную сумму. Оба хранятся в одном классе. Для эксперимента достаточно строк, поэтому форматирование цены здесь не отвлекает от механизма обновлений.

SWIFTObservableOrdersModel.swift
import Combine


final class ObservableOrdersModel: ObservableObject {
    @Published var status = "New"
    @Published var total = "1990 RUB"


    func changeStatus(round: Int) {
        status = "Status \(round)"
    }
}

Первый блок показывает статус, второй читает только сумму. Счётчики в BodyProbe нужны для эксперимента, _printChanges() печатает причину обновления представления. Это диагностический API с подчёркиванием, в приложении его не используют.

SWIFTOrderBlocks.swift
struct ObservableStatusBlock: View {
    @ObservedObject var model: ObservableOrdersModel


    var body: some View {
        BodyProbe.statusBodyCount += 1
        let _ = Self._printChanges()
        return Text(model.status)
    }
}


struct ObservableDetailsBlock: View {
    @ObservedObject var model: ObservableOrdersModel


    var body: some View {
        BodyProbe.detailsBodyCount += 1
        let _ = Self._printChanges()
        return Text("Total: \(model.total)")
    }
}

У ObservableObject по умолчанию есть objectWillChange. Когда меняется любое свойство @Published, издатель сообщает об этом до записи нового значения. Оба блока подписаны на один объект через @ObservedObject, поэтому оба получают сигнал. Какое именно свойство изменилось, подписчику не сообщается.

Из этого следует полезный критерий перехода: если два представления читают разные свойства одной модели, есть шанс увидеть лишние вызовы body. Если вся модель относится к одному небольшому экрану, разница может остаться незаметной.

Модель на Observation

Observation входит в Swift 5.9, а интеграция со SwiftUI доступна начиная с iOS 17 и синхронных выпусков других платформ. Макрос применяют к классу. Поддержку структур в SE-0395 не включили, поэтому замена начинается не с изменения типа модели, а с новой аннотации класса.

SWIFTObservationOrdersModel.swift
import Observation


@Observable
final class ObservationOrdersModel {
    var status = "New"
    var total = "1990 RUB"


    func changeStatus(round: Int) {
        status = "Status \(round)"
    }
}

@Published больше не нужен. Макрос сам добавляет классу соответствие Observable и код регистрации доступа к хранимым свойствам. Если служебное свойство наблюдать не требуется, его помечают @ObservationIgnored.

Вычисляемое свойство тоже участвует в отслеживании, когда его геттер читает наблюдаемые хранимые свойства. Например, isReady зависит от status:

SWIFTObservationOrdersModel+Computed.swift
extension ObservationOrdersModel {
    var isReady: Bool {
        status == "Ready"
    }
}

Здесь зависимость создаёт обращение к status, а не сравнение итогового Bool. Если вычисляемое свойство обращается к внешнему хранилищу, автоматической связи нет: геттер и изменение должны сами зарегистрировать доступ через сгенерированные access(keyPath:) и withMutation(keyPath:).

Есть и граница у вложенных данных. Изменение массива items затрагивает наблюдателей этого массива. Изменение свойства одного элемента не равносильно замене элемента или всего массива. Если item тоже является экземпляром класса с @Observable, чтение item.name в body создаёт зависимость от name, а не от самого факта наличия item внутри items.

Как меняются property wrappers

Перенос модели затрагивает и представления, но соответствия получаются короткими.

До ObservationПосле ObservationКогда применять

Для наших блоков достаточно обычного свойства:

SWIFTObservationOrderBlocks.swift
struct ObservationStatusBlock: View {
    let model: ObservationOrdersModel


    var body: some View {
        BodyProbe.statusBodyCount += 1
        let _ = Self._printChanges()
        return Text(model.status)
    }
}


struct ObservationDetailsBlock: View {
    let model: ObservationOrdersModel


    var body: some View {
        BodyProbe.detailsBodyCount += 1
        let _ = Self._printChanges()
        return Text("Total: \(model.total)")
    }
}

Обертка @ObservedObject исчезла, но представления не потеряли обновления. Во время вычисления body SwiftUI видит обращения к model.status и model.total. Возникают две разные зависимости. Присваивание нового status затрагивает первый блок и не затрагивает второй.

Чтение свойства важнее места хранения объекта. Промежуточное представление может принять модель и передать её дальше, не читая ничего в собственном body. Тогда у промежуточного представления нет зависимости от этих свойств. Но если родитель подставит другой объект в параметр, значение самого представления изменится, и SwiftUI обновит его уже по этой причине.

Сколько раз вызывается body

Мы собрали оба варианта одним исходником на Mac mini с Xcode 26.4.1 и Apple Swift 6.3.1. Deployment target: iOS 17. Запускали на симуляторе iPhone 17 Pro с iOS 26.4.1 в режиме языка Swift 6.

Перед замером приложение прогревалось, затем счётчики обнулялись. В каждом раунде менялся только status. Через 100 миллисекунд программа печатала оба счётчика. Всего выполнено три новых процесса для каждой модели, по пять изменений в процессе.

МодельstatusBody на изменениеdetailsBody на изменениеВсего за 15 изменений
ObservableObject и @Published1115 и 15
@Observable1015 и 0

В первом раунде _printChanges() показал разницу в причинах:

TEXT
ObservableStatusBlock: _model changed.
ObservableDetailsBlock: _model changed.
RESULT scenario=observable-object round=1 statusBody=1 detailsBody=1


ObservationStatusBlock: \ObservationOrdersModel.status changed.
RESULT scenario=observation round=1 statusBody=1 detailsBody=0

Старый механизм сообщает об изменении _model. Новый называет конкретный status. Блок суммы во втором случае не пересчитывался, потому что его зависимость total не менялась.

Это количество вызовов body, а не время рендеринга и не расход CPU. Мы специально взяли минимальную иерархию, где оба блока напрямую работают с моделью. Из результата нельзя переносить конкретные числа на любой экран, но сам механизм виден: Observation регистрирует доступ к свойству, а ObservableObject сообщает об объекте целиком.

Кто владеет моделью

@Bindable и обычное свойство передают ссылку, но не выбирают владельца. Если контейнер создаёт модель как источник истины, используем @State:

SWIFTObservationEnvironmentInstallation.swift
struct ObservationEnvironmentInstallation: View {
    @State private var model = ObservationOrdersModel()


    var body: some View {
        ObservationEnvironmentScreen()
            .environment(model)
    }
}

В эксперименте мы сохранили ObjectIdentifier модели, заставили корневое представление перерисоваться и сравнили идентификатор повторно. Во всех шести запусках получили observationStateSame=true. Для старого варианта с @StateObject результат тоже был observableStateObjectSame=true. Смена identity представления это другое событие: SwiftUI создаёт состояние заново.

До Xcode 27 выражение ObservationOrdersModel() могло выполняться повторно при создании значения представления, хотя SwiftUI сохраняло прежний управляемый экземпляр. Поэтому тяжёлая работа и побочные эффекты в инициализаторе оставались плохой идеей.

В Xcode 27 @State стал макросом, и начальное значение класса создаётся лениво один раз за время жизни представления. Это поведение работает и на iOS 17 при сборке новым Xcode. У нас установлен Xcode 26.4.1, поэтому новую ленивую инициализацию мы не запускали и опираемся здесь на техническую заметку Apple TN3211. Там же разобраны несовместимые случаи с присваиванием @State в init.

Двустороннее соединение и окружение

Для чтения status хватает let model. Для $model.status нужен @Bindable: его проекция создаёт Binding к изменяемому свойству наблюдаемого класса.

SWIFTObservationBindableEditor.swift
struct ObservationBindableEditor: View {
    @Bindable var model: ObservationOrdersModel


    var body: some View {
        TextField("Status", text: $model.status)
    }
}

Владельца эта обёртка не добавляет. Если редактор получит новый экземпляр модели, он будет работать уже с ним, а время жизни объекта по-прежнему определяет контейнер.

Окружение теперь принимает объект через .environment(model). Чтение выполняется по конкретному типу:

SWIFTObservationEnvironmentScreen.swift
struct ObservationEnvironmentScreen: View {
    @Environment(ObservationOrdersModel.self) private var model


    var body: some View {
        Text(model.status)
    }
}

В SDK 26.4 это объявление даёт неопциональную модель. Наш вариант с if let model не скомпилировался именно потому, что разворачивать там нечего. Если объект может отсутствовать, тип свойства явно объявляют опциональным: @Environment(ObservationOrdersModel.self) private var model: ObservationOrdersModel?. Чтение неопциональной модели без установки завершится ошибкой во время выполнения. Для объекта одного типа в одной ветке иерархии окружение хранит одно значение, nil в модификаторе убирает его.

Observations вне SwiftUI

SE-0395 добавил модель и регистрацию чтения свойств. В Swift 6.2 появился отдельный потребитель этого механизма: Observations из SE-0475, доступный на iOS 26 и синхронных выпусках других платформ. Это AsyncSequence результатов замыкания. Он не заменяет @Observable и не управляет пересчётом body.

SWIFTObservationsProbe.swift
import Observation


@Observable
final class OrderStatusModel {
    var status = "New"
}


@main
struct ObservationsProbe {
    @MainActor
    static func main() async {
        let model = OrderStatusModel()
        var iterator = Observations { model.status }.makeAsyncIterator()


        if let initial = await iterator.next() {
            print("initial=\(initial)")
        }


        model.status = "Ready"


        if let changed = await iterator.next() {
            print("changed=\(changed)")
        }
    }
}

На Apple Swift 6.3.1 программа напечатала:

TEXT
initial=New
changed=Ready

Замыкание читает model.status, поэтому последовательность знает, какие изменения отслеживать. Первый вызов next() асинхронно вычисляет начальное значение. Следующие значения поступают после изменений зависимостей. При быстрой серии изменений потребитель может не увидеть каждое промежуточное состояние: транзакции объединяют изменения до целостного текущего значения.

Изоляция остаётся ответственностью автора модели. Observations не делает гонку безопасной. В примере Observations наследует @MainActor от main(). На этом же акторе выполняются все обращения к созданному экземпляру модели. Если нужен обычный синхронный didSet, асинхронная последовательность для этого не подходит.

Низкоуровневый withObservationTracking тоже существует, но его onChange вызывается один раз на первом подходящем изменении и срабатывает на границе willSet. Для постоянной подписки наблюдение регистрируют заново. В SwiftUI эту работу выполняет сам фреймворк, вручную вызывать функцию в body не нужно.

Одно правило для проекта и ассистента

Если в сгенерированном коде встретились ObservableObject и @StateObject, проверьте минимальную версию приложения. Для iOS 17 или новее выбор можно зафиксировать в AGENTS.md:

MARKDOWNAGENTS.md, фрагмент
- Для новых SwiftUI-моделей используйте @Observable.
- Модель, созданную представлением, храните в @State.
- Для $model.property применяйте @Bindable.
- Не добавляйте ObservableObject, @Published и @StateObject
  без требования поддержать iOS 16 или существующий Combine-контракт.

Проверка остаётся за компилятором и поведением экрана. После миграции стоит повторить наш эксперимент на собственных блоках: изменить одно свойство, посмотреть _printChanges() и убедиться, что представления читают именно те зависимости, которые ожидает разработчик.

В Xcode 27 Apple добавила SwiftUI Specialist Skill и What's New In SwiftUI Skill для Coding Assistant. Для других инструментов навыки экспортируют командой xcrun agent skills export. Навык помогает найти современный API, но строка про минимальную версию и принятые в команде обёртки всё равно остаётся в контексте проекта. На установленном у нас Xcode 26.4.1 эти навыки недоступны, поэтому мы не запускали их.

Вопросы на собеседовании

?Чем @Observable отличается от ObservableObject при обновлении SwiftUI?›

ObservableObject сообщает подписчику об изменении объекта через objectWillChange, когда меняется любое @Published свойство. SwiftUI с Observation регистрирует конкретные свойства, прочитанные при вычислении body, и обновляет представление при изменении этих зависимостей.

?Почему для @Observable используют @State, а не @StateObject?›

@StateObject связан с протоколом ObservableObject. Для модели @Observable источник истины хранят в @State. SwiftUI сохраняет экземпляр за представлением и сбрасывает состояние при смене identity.

?Чем @Bindable отличается от @State?›

@State управляет хранением источника истины. @Bindable создаёт Binding к свойствам уже существующей наблюдаемой модели и не выбирает её владельца.

?Что произойдёт с ObservationDetailsBlock после model.status = "Ready"?›
SWIFT
struct ObservationDetailsBlock: View {
    let model: ObservationOrdersModel


    var body: some View {
        print("details body")
        return Text("Total: \(model.total)")
    }
}

Нового вызова body из-за этого присваивания не будет: блок читает total, а изменился status. В нашем эксперименте после 15 таких изменений счётчик остался равен нулю.

?Заменяет ли Observations макрос @Observable?›

Нет. Макрос добавляет классу механизм отслеживания доступа. Observations использует этот механизм и возвращает асинхронную последовательность результатов замыкания.

Итог

  • ObservableObject сообщает об изменении объекта, а Observation регистрирует обращения к конкретным свойствам.
  • Для новой модели на iOS 17+ используем @Observable class, убираем @Published, а владельца храним в @State.
  • Обычная передача модели не требует @ObservedObject. Для $model.property нужен @Bindable, для окружения .environment(model) и @Environment(Model.self).
  • На проверенном экране 15 изменений статуса вызвали 15 пересчётов блока суммы со старой моделью и ни одного с @Observable.
  • Observations из Swift 6.2 работает с результатами замыкания как AsyncSequence и не отвечает за обновление SwiftUI.

Практика

  1. Возьмите экран с двумя блоками и моделью ObservableObject. Оставьте в одном блоке только неизменяемое свойство, измените другое и запишите причины через _printChanges().
  2. Перенесите модель на @Observable, обновите обёртки и повторите тот же сценарий. Сверьте не внешний вид, а число вызовов body и идентичность модели до и после перерисовки.
  3. Добавьте TextField для редактирования одного свойства через @Bindable. Затем уберите @Bindable и объясните, почему обращение $model.status больше не компилируется.
  4. Напишите Observations { model.status }, получите начальное и следующее значение через итератор. Отдельно проверьте серию быстрых присваиваний и сравните число изменений с числом полученных значений.
