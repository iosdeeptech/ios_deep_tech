Ошибки изоляции Swift 6. Чем заменить unchecked Sendable и другие заглушки

Почему после unchecked Sendable сборка проходит, а счётчик теряет обновления. Исправляем общий доступ через actor, Mutex и sending и разбираем границу с MainActor.

#swift#concurrency#sendable

В 4. Sendable мы говорили о типах, которые можно передавать между задачами. При миграции на Swift 6 вопрос становится практическим: компилятор ругается на изменяемое свойство, мы добавляем @unchecked Sendable, и проект снова собирается. Что изменилось в работе программы?

Несколько загрузок заканчиваются одновременно, каждая увеличивает общий счётчик на единицу. После окончания всех загрузок модель экрана читает результат. У счётчика всего одно поле, но для правильного ответа нужно защитить и изменение, и чтение.

!

Нужно знать, что такое Sendable и изоляция на акторе. Перед чтением полезно освежить 4. Sendable, 6. Actor isolation и 2. Actor Reentrancy.

Ошибка ушла, обновления потерялись

SWIFTDownloadStats.swift
final class DownloadStats: Sendable {
    var completed = 0


    func recordCompletion() {
        completed += 1
    }
}

В режиме Swift 6 класс не собирается:

TEXT
error: stored property 'completed' of 'Sendable'-conforming class 'DownloadStats' is mutable

Два потока могут одновременно читать и менять completed. Запись += 1 не делает всю операцию атомарной. Оба потока могут прочитать одно значение, прибавить к нему единицу и записать одинаковый результат. Одна прибавка потеряется. Это лишь один возможный эффект гонки, рассчитывать на конкретное поведение такого кода нельзя.

Добавим @unchecked и воспроизведём ситуацию без настоящих сетевых запросов:

SWIFTUnchecked.swift
import Dispatch


final class DownloadStats: @unchecked Sendable {
    var completed = 0


    @inline(never)
    func recordCompletion() {
        completed += 1
    }
}


let stats = DownloadStats()
DispatchQueue.concurrentPerform(iterations: 100_000) { _ in
    stats.recordCompletion()
}
print(stats.completed)

concurrentPerform ждёт окончания всех итераций. Поэтому после него мы ожидаем 100000, а не промежуточное значение. @inline(never) нужен только для воспроизводимого опыта: он оставляет отдельный вызов метода в оптимизированной сборке.

Мы собрали пример с -O и запустили 20 раз на Mac mini с Apple silicon. Первый запуск вывел 31039. Ни один из 20 не получил ожидаемые 100000. Число не характеризует скорость и не предсказывает результат следующего запуска. Оно показывает, что добавленная пометка не защитила счётчик.

Все примеры ниже проверены Apple Swift 6.3.1 из Xcode 26.4.1. Для консольных программ использовали режим Swift 6, -strict-concurrency=complete и изоляцию по умолчанию nonisolated. Флаги Approachable Concurrency не включали. Версия компилятора и режим языка здесь разные настройки:

Тот же Swift 6.3.1Обычный Sendable с varunchecked Sendable
Режим Swift 5, strict concurrency completeпредупреждение о свойствесобирается
Режим Swift 6ошибка о свойствесобирается

В проекте с MainActor по умолчанию сам класс может получить изоляцию. Тогда условия уже другие. Как найти эти настройки, разобрано в предыдущей статье про Task.

Что мы обещаем через unchecked

По SE-0302 @unchecked Sendable передаёт проверку безопасности типа его автору. Компилятор принимает соответствие Sendable, не доказывая его по хранимым свойствам. Блокировка, копия объекта или очередь при этом не появляются.

В старой статье про Sendable формулировка «отключает проверки компилятора в данном классе/структуре» слишком широкая. Пометка касается проверки соответствия Sendable. Она не отменяет правила акторной изоляции у всего остального кода.

У класса с собственной синхронизацией такое обещание может быть правдой. Но тогда надо проверить все обращения к состоянию, включая чтение для логов, вычисляемые свойства и возвращаемые наружу ссылки. Одного закрытого сеттера недостаточно, если остаётся метод, который читает поле без защиты.

У нашего счётчика собственной синхронизации нет. Выберем, кому принадлежит completed.

Состояние принадлежит актору

SWIFTActorStats.swift
actor DownloadStats {
    private var completed = 0


    func recordCompletion() {
        completed += 1
    }


    func snapshot() -> Int {
        completed
    }
}

Из другой изоляции обращаемся через await. Для проверки создадим 10 000 дочерних задач и дождёмся каждой:

SWIFT
@main
struct Main {
    static func main() async {
        let stats = DownloadStats()
        await withTaskGroup(of: Void.self) { group in
            for _ in 0..<10_000 {
                group.addTask {
                    await stats.recordCompletion()
                }
            }
        }
        print(await stats.snapshot())
    }
}

В проверке получили 10000. Метод recordCompletion() синхронный, внутри него нет точки приостановки. Пока он меняет счётчик, другой вызов на этом акторе не вмешается в изменение. Изоляция распространяется и на snapshot(), поэтому чтение соблюдает то же правило.

Если между чтением и записью появится await, надо заново проверить логику. За время приостановки состояние может измениться. Это reentrancy, а не гонка памяти: актор защищает отдельные участки исполнения, но не обещает неизменность данных через приостановку.

Актор подходит сервису, которым пользуется асинхронный код. Для состояния экрана ту же принадлежность часто выражают через @MainActor. Помечать им тяжёлый расчёт только ради сборки не стоит: место исполнения расчёта тоже изменится.

Нужен синхронный доступ

Предположим, счётчик вызывает старый синхронный API. Переводить этот API на async сейчас нельзя. Можно защитить короткую операцию через Mutex из модуля Synchronization:

SWIFTMutexStats.swift
import Dispatch
import Synchronization


final class DownloadStats: Sendable {
    private let completed = Mutex(0)


    func recordCompletion() {
        completed.withLock { $0 += 1 }
    }


    func snapshot() -> Int {
        completed.withLock { $0 }
    }
}


let stats = DownloadStats()
DispatchQueue.concurrentPerform(iterations: 100_000) { _ in
    stats.recordCompletion()
}
print(stats.snapshot())

Получили 100000. У класса обычное проверяемое соответствие Sendable. Он хранит let со значением Mutex, а изменяемый Int находится внутри мьютекса. И увеличение, и чтение проходят через withLock.

Под капотом Mutex хранит блокировку и ячейку со значением. В исходнике Swift 6.3.1 метод withLock сначала захватывает блокировку, ставит её освобождение в defer, затем передаёт значение замыканию через inout. Даже если замыкание выбросит ошибку, блокировка освободится.

Сам Mutex внутри стандартной библиотеки объявлен @unchecked Sendable. Это ручная гарантия низкоуровневой реализации. Прикладной класс пользуется этой гарантией через ограниченный API и не обязан повторять @unchecked у себя.

!

Блокировка должна покрывать всю операцию. Если отдельно защитить чтение и отдельно запись, между ними всё ещё может вмешаться другой поток. Для увеличения счётчика чтение, прибавление и запись должны находиться в одном withLock.

Mutex нерекурсивный. Нельзя, удерживая его, снова вызвать метод, который берёт ту же блокировку. Замыкание синхронное, await внутри него недопустим. Ожидание занятой блокировки блокирует поток, поэтому под ней оставляют короткую работу с данными, а не сеть или долгий расчёт.

По SDK Mutex доступен начиная с iOS 18 и macOS 15. Для более старого deployment target нужен другой доступный механизм с тем же правилом доступа. Замена на unchecked совместимость не решает.

Другому коду нужен результат, а не счётчик

Иногда общий изменяемый объект вообще не нужен за пределами сервиса. Экрану достаточно числа завершённых загрузок. Вернём снимок:

SWIFT
struct DownloadSnapshot: Sendable {
    let completed: Int
}

Метод актора создаёт его из своего completed, а получатель читает собственное значение. Если счётчик после этого увеличится, уже полученный снимок не изменится. Это подходит для отображения состояния на конкретный момент. Для последующих обновлений нужно запросить новый снимок или отдельно организовать поток событий.

Не любая структура решает проблему. Если вместо Int положить в неё ссылку на тот же изменяемый класс, доступ к общему объекту останется. Явное Sendable полезно здесь тем, что компилятор проверит и типы свойств.

Объект нужен целиком, но только одной стороне

Для передачи готовой пачки загрузок подходит другая модель. Один участок кода заполняет объект, затем отдаёт его хранилищу и больше к нему не обращается:

SWIFTSending.swift
final class DownloadBatch {
    var completed = 0
}


actor DownloadStore {
    private var current: DownloadBatch?


    func accept(_ batch: sending DownloadBatch) {
        current = batch
    }


    func snapshot() -> Int {
        current?.completed ?? 0
    }
}


@main
struct Main {
    static func main() async {
        let store = DownloadStore()
        let batch = DownloadBatch()
        batch.completed = 3
        await store.accept(batch)
        print(await store.snapshot())
    }
}

Программа выводит 3. Класс DownloadBatch не стал Sendable. Параметр sending требует, чтобы передаваемое значение можно было отделить от кода вызывающей стороны. Анализ областей изоляции из SE-0414 учитывает и потенциальные связанные ссылки, а SE-0430 позволяет выразить передачу в сигнатуре.

Если после await store.accept(batch) добавить batch.completed += 1, тот же компилятор отвечает:

TEXT
error: sending 'batch' risks causing data races

Сохранённое второе имя объекта тоже не даёт права продолжать его менять. Проверяется область связанных значений, а не только переменная с именем batch. sending не делает копию и не добавляет блокировку. Он подходит для передачи владения доступом, но не для счётчика, которым должны одновременно пользоваться обе стороны.

Что делать с остальными «исправлениями»

nonisolated(unsafe)

В исходном классе можно оставить обычное Sendable, а у completed написать nonisolated(unsafe). В нашем опыте такой класс тоже собрался и тоже потерял обновления.

Эта пометка снимает статическую проверку изоляции конкретного хранилища. Она уместна, когда доступ уже защищён правилом, которое компилятор не может выразить. Для нашего счётчика такого правила не было. Спрятать предупреждение на уровне свойства ничем не помогло.

Разница с обычным nonisolated существенная. Обычная пометка описывает доступ без акторной изоляции, а компилятор продолжает проверять, допустим ли он. Вариант unsafe оставляет соответствующую часть доказательства разработчику. Подробности этого исключения описаны в SE-0412.

preconcurrency у импорта

Если счётчик приходит из старой библиотеки, можно встретить @preconcurrency import LegacyDownloadKit. В отдельном опыте мы собрали библиотеку с изменяемым LegacyDownloadStats в режиме Swift 5 и захватили её объект в @Sendable-замыкании приложения. Обычный импорт в режиме Swift 6 дал ошибку захвата non-Sendable типа. С @preconcurrency import этот пример собрался.

Внутри библиотеки ничего не изменилось. Пометка ослабила диагностику на границе зависимости. Она может понадобиться для постепенной миграции, когда аннотации библиотеки неполны, а реальное правило использования известно. Тогда рядом должен быть адаптер, который это правило сохраняет, например изоляция всех обращений на одном акторе.

Это не универсальное отключение ошибок Swift 6. Набор и серьёзность диагностик зависят от контекста; правила приведены в SE-0337. Если такой же небезопасный класс объявлен в нашем модуле, пометка на импорте чужого модуля его не исправляет.

assumeIsolated и главная очередь

Перенесём результат в модель экрана:

SWIFT
@MainActor
final class DownloadModel {
    var completed = 0
}

Старый API вызывает completion в глобальной очереди. Внутри него попытались обновить модель так:

SWIFT
MainActor.assumeIsolated {
    model.completed += 1
}

Код собрался, но в нашем запуске остановил процесс с SIGTRAP.

assumeIsolated не планирует работу на главном акторе. Он синхронно проверяет, что текущий исполнитель уже подходит. В установленном SDK перед выполнением замыкания вызывается проверка исполнителя MainActor. Её путь в рантайме можно проследить в Actor.cpp на теге Swift 6.3.1. При нарушении программа завершается. Это проверка во время исполнения вместо статического доказательства.

Когда completion действительно может прийти с другой очереди, нужен переход. Так выглядит проверенный вариант; continuation здесь только позволяет дождаться обновления в консольном опыте:

SWIFT
import Dispatch


@main
struct Main {
    static func main() async {
        let model = DownloadModel()
        await withCheckedContinuation { continuation in
            DispatchQueue.global().async {
                Task { @MainActor in
                    model.completed += 1
                    continuation.resume()
                }
            }
        }
        print(model.completed)
    }
}

Получили 1. Обновление отложено до выполнения задачи на главном акторе. Если синхронный callback обязан сразу вернуть результат, создание такой задачи не сохранит его контракт: API придётся адаптировать иначе.

DispatchQueue.main.async тоже действительно ставит блок в главную очередь, поэтому считать его простым подавлением ошибки нельзя. Но он защищает только код в этом блоке. Если другие места читают тот же счётчик из глобальной очереди, общая модель доступа остаётся неверной. @MainActor у самой модели позволяет выразить правило для всех её обращений.

assumeIsolated оставляют для границы, где API уже гарантирует нужного исполнителя, но его тип этого не выражает. Проверить, что «сейчас вроде главный поток», недостаточно для общего доказательства акторной изоляции.

Синхронный протокол у модели экрана

Ещё один случай для ручного assumeIsolated: протокол требует синхронный метод без изоляции, а модель хранит данные на главном акторе. Начиная со Swift 6.2 соответствие протоколу можно само ограничить главным актором, как описывает SE-0470.

SWIFT
protocol SummaryProviding {
    func summary() -> String
}


@MainActor
final class DownloadModel: @MainActor SummaryProviding {
    var completed = 3


    func summary() -> String {
        "Завершено: \(completed)"
    }
}


@MainActor
func render<T: SummaryProviding>(_ value: T) -> String {
    value.summary()
}

Вторая пометка @MainActor относится к соответствию SummaryProviding. В проверке render(DownloadModel()) на главном акторе вернул Завершено: 3. Использование соответствия из неизолированного вызывающего кода дало ошибку main actor-isolated conformance ... cannot be used in nonisolated context.

Старый callback от этого не переезжает на главный актор. Если библиотека требует вызывать метод из любого контекста, её контракт надо учитывать отдельно. Не путайте изолированное соответствие с @preconcurrency у соответствия: во втором случае часть проверок может переноситься на время исполнения по SE-0423.

Как проверить исправление

У небезопасного счётчика число иногда может случайно совпасть с ожидаемым. Поэтому успешный запуск теста не доказывает отсутствие гонки. Мы отдельно собрали тот же Unchecked.swift с Thread Sanitizer:

SHELL
xcrun swiftc -swift-version 6 -default-isolation nonisolated -strict-concurrency=complete -O -sanitize=thread Unchecked.swift -o UncheckedTSan
TSAN_OPTIONS=halt_on_error=1:external_symbolizer_path= ./UncheckedTSan

Санитайзер сообщил WARNING: ThreadSanitizer: Swift access race в DownloadStats.recordCompletion(). Параметры запуска останавливают опыт на первой ошибке и отключают внешний символизатор, который зависал в нашей среде. Варианты с актором и Mutex вернули ожидаемые числа без отчётов санитайзера в этом сценарии. При этом даже чистый запуск покрывает только те пути и пересечения обращений, которые случились во время запуска.

Для миграции вместе с ассистентом полезнее описать доступ к данным, чем попросить «убрать все concurrency errors». Например:

TEXT
Swift 6, strict concurrency complete, default isolation nonisolated.
Счётчик вызывается из нескольких фоновых контекстов.
Интерфейс recordCompletion должен остаться синхронным.
Минимальная версия iOS 18. Все чтения должны быть защищены.
Предложи исправление и объясни, что защищает чтение, изменение и возврат результата.

В CI собирайте целевой модуль в выбранном режиме Swift, проверяйте параллельное увеличение и запускайте подходящие сценарии с Thread Sanitizer. Появление @unchecked Sendable, nonisolated(unsafe) или нового @preconcurrency должно получать отдельное объяснение на ревью. Само наличие пометки ещё не доказывает ошибку, но показывает место, где нужны дополнительные основания.

Вопросы на собеседовании

?Что выведет счётчик с unchecked Sendable после 100 000 параллельных увеличений?›

Предсказать нельзя: в программе гонка данных. В нашем запуске было 31039, но это не гарантированный результат. Даже 100000 в одном запуске не доказывает безопасность.

?Почему у класса с Mutex обычное Sendable, если внутри Mutex используется unchecked?›

Класс хранит неизменяемое Sendable-значение Mutex. Ручную гарантию внутреннего изменяемого состояния предоставляет реализация мьютекса. Прикладной класс пользуется его API и не выпускает обходные обращения к защищаемым данным.

?Можно ли вернуть из Mutex изменяемый объект, а потом менять его снаружи?›

Такая схема может дать доступ в обход блокировки. Для нашего примера наружу уходит Int, а не ссылка на внутреннее изменяемое состояние. В общем случае надо проверять сигнатуру, передачу области и все оставшиеся алиасы.

?Делает ли sending обычный класс потокобезопасным?›

Нет. Он выражает передачу значения между областями изоляции при ограничениях на дальнейшее использование. Для одновременного доступа к общему изменяемому объекту нужна другая модель.

?Чем assumeIsolated отличается от Task с MainActor?›

assumeIsolated сразу проверяет текущего исполнителя и синхронно выполняет замыкание либо останавливает процесс. Task { @MainActor in ... } создаёт задачу, которая выполняет тело на главном акторе. Это меняет момент выполнения и не даёт синхронно вернуть результат из callback.

Итог

  • @unchecked Sendable переносит проверку безопасности типа на автора. Синхронизацию он не добавляет.
  • Общий счётчик можно изолировать на акторе или целиком спрятать в Mutex. Чтения должны следовать тому же правилу, что и записи.
  • Снимок результата уменьшает число мест, которым нужен общий объект. sending позволяет передать non-Sendable объект, если вызывающая сторона больше не использует связанную область.
  • assumeIsolated проверяет исполнителя. Переход на другой исполнитель делают отдельным действием.
  • Сборка, стресс-тест и Thread Sanitizer проверяют разные вещи. Ни один зелёный запуск не заменяет понятную модель доступа к состоянию.

Практика

1. Добавьте к счётчику число неудачных загрузок. Метод snapshot() должен возвращать оба числа как одно согласованное состояние. Сделайте варианты с актором и Mutex.

✓На что смотреть›

Для мьютекса оба числа хранятся в одной защищаемой структуре, а снимок получается одним withLock. В акторе синхронный snapshot() читает оба поля без await между ними. Отдельно защищённые чтения могут показать значения из разных моментов.

2. В примере с sending сохраните вторую ссылку на batch до передачи и попробуйте изменить объект через неё после accept. Сравните диагностику с прямым обращением к batch.

✓Ожидаемый вывод›

Второе имя не создаёт независимый объект. Компилятор должен учитывать связь ссылок при проверке использования после передачи. Если хотите сохранить данные у отправителя, заранее получите независимое Sendable-значение.

3. Вернитесь к задаче 13 про кеш. Можно ли обойтись без отдельного actor, если другие механизмы синхронизации запрещены?

✓Решение›

Можно, если кеш целиком принадлежит уже существующему актору либо используется только в одном изолированном контексте. Если под запрет попадает и такая изоляция, остаётся не разделять изменяемый кеш между конкурентными контекстами. Общий изменяемый кеш с одновременным доступом и полным запретом синхронизации безопасным не станет. Mutex нарушает условие задачи, а unchecked ничего не защищает.
