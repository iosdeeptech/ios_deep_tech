Task, Task.detached и атрибут concurrent в Swift 6.2

Один пример с Task во viewDidLoad. Где выполняется долгий расчёт и какое исправление освобождает главный поток при разных режимах Swift и настройках цели в Xcode 26.

#swift#concurrency#tasks#xcode

Вопрос с собеседования: во viewDidLoad запускают Task с долгим синхронным расчётом, и экран замирает. Почему так происходит и как это исправить? В статье про Task.detached мы отвечали так: перенести расчёт в Task.detached или в отдельный сервис. В Swift 6.2 ответ зависит от настроек цели. Если расчёт вынесен в функцию или класс без пометок, как в примере ниже, в новом проекте Xcode 26 оба способа оставляют его на главном потоке. При любых настройках главный поток освобождает асинхронная функция с атрибутом @concurrent.

!

Нужно знать, что такое задача и изоляция на акторе. Перед чтением полезно освежить Task и Task.detached, 5. Global Actor и 6. Actor isolation.

Пример

SWIFTReportViewController.swift
import UIKit


func buildReport() -> String {
    // остановит приложение, если функция выполняется на главном потоке
    dispatchPrecondition(condition: .notOnQueue(.main))
    var total = 0
    for value in 0..<20_000_000 { total += value % 7 }   // долгий синхронный расчёт
    return "Итого: \(total)"
}


final class ReportViewController: UIViewController {
    private let label = UILabel()


    override func viewDidLoad() {
        super.viewDidLoad()
        view.addSubview(label)
        Task {
            let text = buildReport()
            label.text = text
        }
    }
}

Строка с dispatchPrecondition проверяет поток. Если расчёт выполняется на главном потоке, приложение остановится на ней с EXC_BREAKPOINT, и по заморозке экрана гадать не придётся. С этой строкой проверяйте и каждое исправление ниже. Все варианты статьи мы собрали компилятором Swift 6.3.1 из Xcode 26.4.1 и запустили в симуляторе iOS 26.4.

Где выполняется расчёт

Ответ зависит от трёх настроек цели в Build Settings: Swift Language Version, Default Actor Isolation и Approachable Concurrency. Swift 5 и Swift 6 дальше означают режим языка из первой настройки, а не версию компилятора. Новый проект приложения в Xcode 26.4.1 создаётся в режиме Swift 5, с Default Actor Isolation = MainActor и Approachable Concurrency = Yes. В проекте, созданном до Xcode 26 (дальше старый проект), у двух последних настроек значения по умолчанию: nonisolated и No.

Две новые настройки меняют, где выполняется код без пометок:

  • Default Actor Isolation = MainActor (дальше MainActor по умолчанию) делает такой код @MainActor: функции на уровне файла, как buildReport(), типы и их методы.
  • Approachable Concurrency среди прочего запускает асинхронную функцию без изоляции на акторе вызывающего кода. Без этой настройки такая функция уходит с актора в общий пул потоков.

Оба правила и атрибут @concurrent появились в Swift 6.2, а эта версия компилятора входит в Xcode 26. В Xcode 16 компилятор более ранний (в Xcode 16.3 это Swift 6.1). Этих правил и атрибута там нет, и асинхронная функция без изоляции всегда уходит в общий пул, как в старом проекте.

На исходный пример настройки не влияют: Task {} наследует главный актор контроллера, потому что UIKit объявляет UIViewController на главном акторе, и синхронный вызов выполняется на том же потоке. Компилятор при этом молчит.

Исправления

Где выполняется buildReport() в исходном примере и в четырёх исправлениях. В заголовках столбцов значения Default Actor Isolation и Approachable Concurrency:

Вариантnonisolated, No (старый проект)nonisolated, YesMainActor, Yes (новый проект)
Исходный Task {}главный потокглавный потокглавный поток
Task.detachedобщий пулобщий пулглавный поток, предупреждение
async-метод сервисаобщий пул, в Swift 6 ошибкаглавный потокглавный поток
nonisolated async-функцияобщий пулглавный потокглавный поток
@concurrent-функцияобщий пулобщий пулобщий пул

Средний столбец получается, если в старом проекте включить одну Approachable Concurrency. Режим Swift 5 или 6 не меняет, где выполняется код, он меняет только сообщения компилятора. В режиме Swift 5 предупреждение есть только у Task.detached в новом проекте. В режиме Swift 6 оно становится ошибкой, и ещё одна ошибка появляется у сервиса в старом проекте. Остальные ячейки в обоих режимах собираются без предупреждений.

Task.detached

SWIFTviewDidLoad
Task.detached {
    let text = buildReport()
    await MainActor.run { self.label.text = text }
}

Замыкание Task.detached не наследует актор, поэтому без MainActor по умолчанию buildReport() выполняется в общем пуле. В новом проекте эта настройка делает саму функцию @MainActor. Задача переходит на главный актор ради её вызова, и сборка проходит с предупреждением:

TEXT
warning: main actor-isolated global function 'buildReport()' cannot be called from outside of the actor; this is an error in the Swift 6 language mode

Мешает только вызов функции, которую новый проект сделал @MainActor. Расчёт, написанный прямо в замыкании, и nonisolated func buildReport() выполняются в общем пуле при любых настройках. Приоритет и task-local значения задача при этом теряет (Что теряет Task.detached).

Отдельный сервис

SWIFT
final class ReportService {
    func buildReport() async -> String {
        // тот же расчёт
    }
}


// в ReportViewController
private let service = ReportService()


// во viewDidLoad
Task {
    let text = await service.buildReport()
    label.text = text
}

В старом проекте класс без изоляции, и его асинхронный метод уходит в общий пул. В режиме Swift 6 этот вариант там не собирается:

TEXT
error: sending 'self.service' risks causing data races [#SendingRisksDataRace]

Откуда ошибка, разбирает последний вопрос с собеседования. В новом проекте MainActor по умолчанию делает сам класс @MainActor, и метод выполняется на главном акторе. На главный поток метод вернёт и одна Approachable Concurrency без MainActor по умолчанию (средний столбец): метод без изоляции останется на акторе вызывающего кода.

nonisolated async-функция

SWIFT
nonisolated func buildReport() async -> String {
    // тот же расчёт
}


// во viewDidLoad
Task {
    let text = await buildReport()
    label.text = text
}

Явная пометка nonisolated снимает с функции MainActor по умолчанию, но Approachable Concurrency всё равно оставляет асинхронную функцию на акторе вызывающего кода, то есть на главном. В общий пул она уходит только в старом проекте, где Approachable Concurrency выключена. При вызове из исходного Task {} пометка nonisolated у синхронной buildReport() не помогает ни в одном проекте: синхронная функция выполняется там, где её вызвали.

@concurrent

Атрибут @concurrent появился в Swift 6.2 и работает в любом режиме языка. Функция с ним всегда уходит с актора вызывающего кода в общий пул:

SWIFT
@concurrent func buildReport() async -> String {
    // тот же расчёт
}


// во viewDidLoad
Task {
    let text = await buildReport()
    label.text = text   // после await снова главный актор
}

Из пяти вариантов таблицы только этот освобождает главный поток во всех трёх столбцах. Расчёт остаётся частью той же задачи, с её приоритетом и task-local значениями.

!

Две ловушки с @concurrent. Атрибут ставят только на асинхронную функцию. На синхронной buildReport() компилятор при любых настройках отвечает error: cannot use @concurrent on non-async global function 'buildReport()'.

Вторая ловушка в помощниках. Здесь @concurrent-функция вызывает синхронную функцию без пометок:

SWIFT
func sumValues() -> Int {                    // помощник без пометок
    var total = 0
    for value in 0..<20_000_000 { total += value % 7 }
    return total
}


@concurrent func buildReport() async -> String {
    "Итого: \(sumValues())"
}

В новом проекте sumValues() из-за MainActor по умолчанию изолирована на главном акторе. Код собирается с предупреждением, и ради вызова помощника расчёт возвращается на главный поток. Тот же проект в режиме Swift 6 такой код не собирает. В старом проекте помощник без изоляции и выполняется в общем пуле вместе с buildReport(). С пометкой nonisolated func sumValues() -> Int расчёт идёт в общем пуле при любых настройках.

Что теряет Task.detached

Task {}Task.detached
Акторнаследует: во viewDidLoad главный, label меняют напрямуюнет, к интерфейсу возвращаются через await MainActor.run
Приоритетнаследует от места создания, из viewDidLoad .highбез параметра priority по умолчанию .medium
Task-local значениякопируетне видит

Если приоритет расчёта важен, передайте его в Task.detached параметром priority:. Task-local значения, например идентификатор запроса для логов, в такую задачу не попадут. Подробнее о приоритетах в 5. Task Priority, а о том, что получают из task-local значений Task {} и Task.detached, в разборе хранилища Task Local.

Вопрос к ассистенту

Настройки цели в коде не видны, а правильное исправление от них зависит. Добавьте к вопросу ассистенту одну строку с ними. Значения найдите в Build Settings цели поиском по названию настройки. Для нового проекта Xcode 26 строка такая:

TEXT
Настройки цели: Swift Language Version 5, Default Actor Isolation MainActor, Approachable Concurrency Yes, Xcode 26.4.1

Предложенное исправление соберите в своём проекте. Приписка this is an error in the Swift 6 language mode у предупреждения значит, что в режиме Swift 6 эта строка не соберётся. Затем запустите приложение с dispatchPrecondition первой строкой расчёта, как в примере. Если расчёт остался на главном потоке, приложение остановится на этой строке. Проверка срабатывает и в Release-сборке, так что перед релизом её убирают.

Вопросы на собеседовании

Прежде чем раскрыть ответ, сформулируйте свой.

?Почему Task {} во viewDidLoad замораживает экран, хотя задача асинхронная?›

UIViewController объявлен на главном акторе, и Task {} наследует этот актор. Тело задачи встаёт в очередь главного актора и начинает выполняться, когда viewDidLoad уже вернулся, но выполняется оно на главном потоке. Синхронный расчёт занимает этот поток до конца при любых настройках цели.

?Что будет выведено в старом проекте и в новом проекте Xcode 26?›
SWIFT
import UIKit


nonisolated func onMainThread() -> Bool { Thread.isMainThread }


nonisolated func loadReport() async -> Bool {
    onMainThread()
}


final class ReportViewController: UIViewController {
    override func viewDidLoad() {
        super.viewDidLoad()
        Task {
            let before = onMainThread()
            let inside = await loadReport()
            print(before, inside)
        }
    }
}

В старом проекте, в режиме Swift 5 и Swift 6:

TEXT
true false

В новом проекте Xcode 26:

TEXT
true true

Обе функции явно nonisolated, поэтому MainActor по умолчанию их не касается. Синхронная onMainThread() выполняется там, где её вызвали, а тело задачи стоит на главном акторе. Асинхронная loadReport() в старом проекте уходит в общий пул, а в новом из-за Approachable Concurrency выполняется на акторе вызывающего кода.

?Чем Task.detached отличается от Task {}, и какая из них дочерняя задача?›

Task {} наследует актор места создания, приоритет и task-local значения, Task.detached не наследует ничего из этого. Дочерней не будет ни одна. Обе задачи неструктурированные, родителя у них нет, и отмена задачи, внутри которой их создали, до них не доходит. Дочерние задачи создают async let и группы задач. В статье про Task.detached Task {} по ошибке назван дочерней задачей.

?Почему в старом проекте в режиме Swift 6 сервис из свойства контроллера не собирается, а созданный прямо в вызове собирается?›

Сравним await service.buildReport() и await ReportService().buildReport(). service лежит в свойстве контроллера и принадлежит главному актору: к нему обращается любой код контроллера. Асинхронный метод без изоляции в старом проекте выполняется в общем пуле. Пока задача ждёт его на await, главный актор свободен и может обратиться к тому же объекту, поэтому компилятор не разрешает отправить service в пул. Объект из ReportService() создан прямо в вызове и больше нигде не виден, его отправить можно. В режиме Swift 5 обе формы собираются молча. С Approachable Concurrency ошибки нет, потому что метод остаётся на главном акторе, а вместе с ним и расчёт.

Итог

  • Task {} во viewDidLoad выполняет тело на главном акторе при любых настройках. Синхронный расчёт в нём замораживает экран, а сборка проходит без предупреждений.
  • Где выполняется код без пометок, решают две настройки цели. MainActor по умолчанию делает его @MainActor, а Approachable Concurrency оставляет асинхронные функции без изоляции на акторе вызывающего кода. Режим Swift 5 или 6 меняет только сообщения компилятора.
  • В новом проекте Xcode 26 Task.detached с функцией без пометок, async-метод обычного сервиса и nonisolated async-функция оставляют расчёт на главном потоке. @concurrent у асинхронной функции уводит его в общий пул при любых настройках.
  • Task.detached не наследует актор, приоритет и task-local значения. Дочернюю задачу не создаёт ни она, ни Task {}.
  • В вопросе ассистенту называйте режим Swift и две новые настройки цели, а предложенное исправление собирайте и запускайте с dispatchPrecondition.

Практика

Первые две задачи решайте сами, третью вместе с ассистентом.

1. Задача 1 из 1. Практический путь в виде, который собирается. Что выведет этот код?

SWIFT
nonisolated func isMain() -> Bool { Thread.isMainThread }


final class SomeViewController: UIViewController {
    override func viewDidLoad() {
        super.viewDidLoad()
        Task {
            print("Task до foo: \(isMain())")
            await foo()
            print("Task после foo: \(isMain())")
        }
        Task.detached {
            print("detached до foo: \(isMain())")
            await self.foo()
            print("detached после foo: \(isMain())")
        }
    }


    func foo() async {
        print("foo: \(isMain())")
        try? await Task.sleep(for: .seconds(1))
    }
}
✓Решение›
TEXT
detached до foo: false
Task до foo: true
foo: true
foo: true
Task после foo: true
detached после foo: false

Вывод одинаковый при любых настройках цели. foo() объявлен в наследнике UIViewController, поэтому он изолирован на главном акторе и из Task.detached тоже выполняется на главном потоке. Task.detached не помогает, если вызванный метод сам изолирован на главном акторе. После await задача Task.detached возвращается в общий пул. Порядок строк двух задач не гарантирован. У нас первой шла строка detached до foo, потому что тело Task {} ждало очереди на главном акторе.

От исходной задачи код отличается в двух местах: замыкание Task.detached требует явного self.foo(), а поток читает синхронная isMain(), потому что Thread.isMainThread недоступен из асинхронного кода.

2. Задача 8 из 1. Практический путь: на ревью пришёл такой класс модели экрана.

SWIFT
@MainActor
class OnboardingViewModel: ViewModel {
    // ...
}

Какие замечания вы оставите и что изменится, когда модель начнёт расти?

✓Решение›

Для модели экрана @MainActor на классе уместен, потому что её состояние читает интерфейс. Apple советует MainActor по умолчанию для модулей с UI, и в новом проекте Xcode 26 класс изолирован на главном акторе даже без пометки. Когда модель вырастет, на главном потоке будет выполняться весь её код, включая async-методы, а в новом проекте ещё и асинхронные функции без изоляции, которые она вызывает. Тяжёлую работу модель уводит явно, как buildReport() в статье:

SWIFT
@MainActor
final class OnboardingViewModel {
    private(set) var titles: [String] = []


    func load(_ data: Data) async throws {
        titles = try await Self.decodeTitles(data)   // результат вернётся на главный актор
    }


    @concurrent
    private static func decodeTitles(_ data: Data) async throws -> [String] {
        try JSONDecoder().decode([String].self, from: data)
    }
}
