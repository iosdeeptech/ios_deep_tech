В [[1. Как изучать iOS вместе с ассистентом и не терять понимание|статье об обучении с ассистентом]] мы предлагали сначала записать ожидаемый результат, а затем сравнить его с работой программы. Это ожидание можно сразу превратить в тест. Тогда у вас появится пример поведения, который запускается после каждого изменения кода.

Возьмём кеш изображений. Просьба «напиши кеш на два элемента» оставляет несколько вопросов. Что произойдёт при третьей записи? Изменяет ли чтение порядок удаления? Должна ли перезапись существующего ключа вытеснять соседний? Пока ответы не записаны, две разные реализации могут одинаково подходить под такую просьбу.

> [!warning] Нужно знать структуры, словари и Optional в Swift.
> Изображения в примере представлены значениями `Data`. Мы проверяем хранение байтов в памяти, без загрузки из сети и декодирования картинки.

### Сначала определим поведение

Наш `ImageCache` хранит данные по строковому ключу. `capacity` задаёт максимальное количество ключей, а не размер данных в байтах. Отрицательную вместимость передавать нельзя. Для остальных случаев договоримся о следующем:

- запись по существующему ключу заменяет данные, количество ключей не растёт;
- успешное чтение и запись делают ключ последним использованным;
- при переполнении удаляется ключ, которым дольше всего не пользовались;
- при вместимости ноль кеш ничего не сохраняет; чтение неизвестного ключа возвращает `nil`, удаление неизвестного ключа ничего не меняет.

Такую политику вытеснения называют LRU, от Least Recently Used. Она отличается от FIFO, где удаляется первая добавленная запись. Если мы положили `a`, затем `b`, прочитали `a` и положили `c`, LRU должен удалить `b`. В FIFO чтение ничего не меняет, поэтому удалится `a`.

Эти правила нужны и нам, и ассистенту, которому мы поручим реализацию. Тесты будут проверять конкретные последовательности действий из этого описания. Нельзя сначала попросить FIFO, а затем считать ошибкой то, что код не проходит тест для LRU.

### Первый тест до реализации

Swift Testing входит в официальные toolchain Swift 6. В тестовом target достаточно `import Testing`; отдельная зависимость на репозиторий библиотеки для этого примера не нужна. Это описано в [документации Swift Testing](https://github.com/swiftlang/swift-testing#cross-platform-support).

Создайте Swift-пакет `ImageCacheLab` с библиотекой и тестовым target. Реализация будет лежать в `Sources/ImageCacheLab`, тесты в `Tests/ImageCacheLabTests`. Запускать их можно из папки пакета:

```sh
swift test
```

Все примеры проверены на Mac mini с Apple Swift 6.3.1 из Xcode 26.4.1, в режиме Swift 6. Начнём с типа, у которого уже есть нужный интерфейс, но методы ещё ничего не делают:

```swift title="ImageCache.swift"
import Foundation

public struct ImageCache {
    public init(capacity: Int) {}
    public var count: Int { 0 }
    public mutating func insert(_ data: Data, forKey key: String) {}
    public mutating func image(forKey key: String) -> Data? { nil }
    public mutating func remove(forKey key: String) {}
}
```

Теперь проверим одно требование: записанные данные можно получить по тому же ключу.

```swift title="ImageCacheTests.swift"
import Foundation
import Testing
@testable import ImageCacheLab

@Test("Возвращает сохранённые данные")
func returnsInsertedData() throws {
    var cache = ImageCache(capacity: 2)
    let image = Data([1, 2, 3])

    cache.insert(image, forKey: "avatar")
    let result = cache.image(forKey: "avatar")
    let stored = try #require(result)

    #expect(stored == image)
}
```

Здесь видны подготовка данных, действие и проверка результата. Имя ключа ничего не сообщает реализации о том, каким должен быть ответ: ожидаемые байты находятся в самом тесте.

`@Test` помечает функцию как тест. `#expect` проверяет условие и записывает ошибку проверки, если оно ложно. После неудачного `#expect` выполнение теста продолжается. Макрос сохраняет части выражения, поэтому в диагностике можно увидеть фактические значения.

`#require` нужен там, где без выполнения условия следующие шаги теряют смысл. В нашем случае он разворачивает Optional. Если там `nil`, макрос бросает ошибку. С обычным `try` она выходит из этой тестовой функции, и сравнение байтов уже не выполняется. Остальные тесты продолжают работать. Поведение обоих макросов описано в [Expectations](https://github.com/swiftlang/swift-testing/blob/main/Sources/Testing/Testing.docc/Expectations.md).

С заглушкой тест упал. Из сообщения Swift Testing:

```text
Expectation failed: result → nil
```

Это ожидаемая причина: `image(forKey:)` всегда возвращает `nil`. Если бы сборка остановилась из-за отсутствующего импорта или неверного имени метода, до проверки поведения мы бы ещё не дошли.

### От красного к зелёному

Добавим словарь. Пока реализуем сохранение, чтение и удаление, а ограничение вместимости оставим для следующих тестов:

```swift title="ImageCache.swift"
import Foundation

public struct ImageCache {
    private var images: [String: Data] = [:]

    public init(capacity: Int) {}
    public var count: Int { images.count }

    public mutating func insert(_ data: Data, forKey key: String) {
        images[key] = data
    }

    public mutating func image(forKey key: String) -> Data? {
        images[key]
    }

    public mutating func remove(forKey key: String) {
        images.removeValue(forKey: key)
    }
}
```

Первый тест теперь проходит. Это ещё промежуточный вариант: он проигнорирует `capacity: 0` и сохранит любое количество ключей. Следующая проверка должна показать одно из этих нарушений до того, как мы добавим соответствующую логику.

Так устроен цикл red, green, refactor: сначала проверка падает по понятной причине, затем мы реализуем нужное поведение, после этого меняем устройство кода с повторным запуском тестов. Например, можно вынести обновление порядка ключей в отдельный метод. Во время такого рефакторинга ожидаемые результаты сохраняются.

В запросе ассистенту этот порядок можно закрепить прямо:

> Реализуй `ImageCache` по описанному контракту LRU. Меняй только файл реализации. Сначала запусти предоставленные тесты и назови причину падения, затем внеси изменение и повтори запуск. Если тест противоречит контракту, укажи противоречие до изменения кода. Отдельно перечисли требования, для которых в видимом наборе нет проверки.

Запрет на изменение тестов в таком запросе выражает наше намерение. Фактические изменения всё равно нужно смотреть в diff: удалённая проверка, `.disabled()` или изменённое ожидаемое значение могут объяснить зелёный результат.

### Одна проверка с разными входами

Для вместимости не нужны три почти одинаковые функции. Передадим значения через `arguments`:

```swift
@Test("Не превышает вместимость", arguments: [0, 1, 2])
func respectsCapacity(capacity: Int) {
    var cache = ImageCache(capacity: capacity)
    for key in ["a", "b", "c"] {
        cache.insert(Data([1]), forKey: key)
    }
    #expect(cache.count == capacity)
}
```

Swift Testing создаёт отдельный случай для каждого аргумента и показывает значение при ошибке. Здесь после трёх вставок вместимость полностью заполнена, поэтому мы сравниваем количество с `capacity`. Этот тест проверяет размер кеша, но ничего не говорит о том, какие именно ключи остались.

Тесты и их параметризованные случаи по умолчанию могут выполняться параллельно. Каждый наш тест создаёт свой кеш, поэтому его результат не зависит от соседнего запуска. Один общий кеш на весь набор потребовал бы другой организации состояния. Эти правила приведены в [документации параметризации](https://github.com/swiftlang/swift-testing/blob/main/Sources/Testing/Testing.docc/ParameterizedTesting.md) и [параллельного запуска](https://github.com/swiftlang/swift-testing/blob/main/Sources/Testing/Testing.docc/Parallelization.md).

У `@Test` и `@Suite` также есть трейты: параметры для организации и настройки запуска. Например, `.tags(.cache)` объединяет связанные проверки для отбора, а `.disabled()` пропускает тест. Пропущенная проверка не подтверждает поведение кеша.

### Восемь тестов прошли, а политика другая

Мы подготовили восемь видимых тестовых функций: пустой кеш, запись и чтение, неизвестный ключ, перезапись, удаление, удаление неизвестного ключа, ограничение размера и вытеснение без промежуточных чтений. Проверка вместимости параметризована тремя значениями, поэтому эти восемь функций дают десять запусков тестовых случаев.

Затем сделали две реализации вручную: FIFO и LRU. В обеих запускали одинаковые тесты.

FIFO прошёл весь видимый набор. В нём не было чтения или перезаписи старого ключа перед переполнением. Начнём с проверки чтения:

```swift
@Test("Чтение обновляет порядок использования")
func readUpdatesRecency() throws {
    var cache = ImageCache(capacity: 2)
    cache.insert(Data([1]), forKey: "a")
    cache.insert(Data([2]), forKey: "b")
    _ = cache.image(forKey: "a")

    cache.insert(Data([3]), forKey: "c")

    let result = cache.image(forKey: "a")
    let retained = try #require(result)
    #expect(retained == Data([1]))
    #expect(cache.image(forKey: "b") == nil)
    #expect(cache.image(forKey: "c") == Data([3]))
}
```

Порядок для правильной реализации можно проследить без кода. Слева в таблице находится кандидат на удаление:

| Действие | Порядок ключей LRU |
|---|---|
| Записать `a`, затем `b` | `a, b` |
| Прочитать `a` | `b, a` |
| Записать `c` | `a, c`, ключ `b` удалён |

Для отдельного набора мы подготовили ещё 15 тестовых функций. В них вошли чтение и перезапись перед вытеснением, повторные чтения, вместимость один, пустой ключ и другие случаи исходного контракта. На том же toolchain получили:

| Реализация | 8 видимых тестов | 15 дополнительных тестов |
|---|---|---|
| FIFO | Все прошли | 4 теста упали |
| LRU | Все прошли | Все прошли |

В [[Attachments/test-first-swift-testing-for-agent-example.zip|полном примере ImageCacheLab]] лежат оба набора тестов, варианты реализации и команды запуска. Можно повторить каждый шаг таблицы, подставляя FIFO или LRU в файл реализации.

Дополнительный набор здесь проверяет уже заявленные правила. Он не требует от реализации нового поведения задним числом. При работе с ассистентом такой набор можно запускать отдельно после первого решения, чтобы проверить последовательности, которые не были показаны в первоначальном запросе.

### Реализация, которая учитывает чтение

Храним данные в словаре, а порядок ключей в массиве. После успешного чтения или записи переносим ключ в конец. При переполнении убираем первый элемент:

```swift title="ImageCache.swift"
import Foundation

public struct ImageCache {
    private let capacity: Int
    private var images: [String: Data] = [:]
    private var order: [String] = []

    public init(capacity: Int) {
        precondition(capacity >= 0)
        self.capacity = capacity
    }

    public var count: Int { images.count }

    public mutating func insert(_ data: Data, forKey key: String) {
        guard capacity > 0 else { return }
        images[key] = data
        markAsUsed(key)

        if order.count > capacity {
            images.removeValue(forKey: order.removeFirst())
        }
    }

    public mutating func image(forKey key: String) -> Data? {
        guard let data = images[key] else { return nil }
        markAsUsed(key)
        return data
    }

    public mutating func remove(forKey key: String) {
        images.removeValue(forKey: key)
        order.removeAll { $0 == key }
    }

    private mutating func markAsUsed(_ key: String) {
        order.removeAll { $0 == key }
        order.append(key)
    }
}
```

Перед добавлением в конец мы удаляем прежнее вхождение ключа. Иначе два чтения одной картинки создали бы два элемента в массиве порядка, хотя в словаре запись осталась бы одна. Промах чтения возвращает `nil` до изменения порядка.

Метод `image(forKey:)` здесь `mutating`: получение данных меняет порядок использования внутри структуры. Поэтому результат чтения в тесте лучше сначала сохранить в локальную переменную, а затем передать в `#require`. На нашем Swift 6.3.1 это также позволяет избежать ошибки раскрытия макроса при прямом вызове изменяющего метода внутри optional-проверки.

Это учебный кеш. Вместимость считается в ключах, обход массива при обновлении порядка не рассчитан на большой объём, а синхронизации общего доступа в типе нет. Для общего изменяемого состояния понадобится подходящая граница изоляции, как в [[1. Ошибки изоляции Swift 6. Чем заменить unchecked Sendable и другие заглушки|статье про ошибки изоляции Swift 6]]. Для изменения структуры хранения можно оставить те же проверки внешнего поведения.

### Чего не доказывает зелёный запуск

Тест может содержать ошибку. Если при одинаковой последовательности действий одна проверка требует сохранить `a`, а другая требует удалить `a`, сначала нужно вернуться к контракту. Исправление реализации под оба ответа не прояснит, какой вариант нужен приложению.

В исследовании [ImpossibleBench](https://arxiv.org/html/2510.20270v1) авторы специально сделали задачи, в которых тесты противоречат требованиям. Они наблюдали изменение тестов, специальные случаи в реализации и перегрузку операторов сравнения. В одном из экспериментов скрытие тестов снизило успешный обход почти до нуля, но ухудшило решение исходных задач. В другом режиме перед оценкой восстанавливали изменённые тесты. Их правка перестала помогать получить положительный результат, но другие способы обхода сохранились. Это результат их постановки эксперимента, а не частота таких ошибок в обычном iOS-проекте.

Для нашего кеша из этого получается конкретная проверка на ревью: сохранились ли требования, тестовые входы и ожидаемые результаты; нет ли веток специально под строки `a`, `b` и `avatar`. Отдельные новые случаи полезны вместе с чтением реализации. Ни этот набор из 23 тестовых функций, ни запрет редактирования файлов не доказывают правильность программы для всех возможных входов.

### Если у метода есть completion

Для событий в Swift Testing есть `confirmation`. Она считает вызовы подтверждения во время переданной операции и сверяет количество, когда операция завершилась. По умолчанию ожидается ровно один вызов. Это описано в [Testing asynchronous code](https://developer.apple.com/documentation/testing/testing-asynchronous-code).

Если `start()` только запланировал callback и сразу вернулся, одна обёртка `await confirmation { ... }` не будет ждать этот callback. Нужно дождаться завершения самой операции; это отличие от ожиданий XCTest отдельно объяснено в [руководстве по миграции](https://github.com/swiftlang/swift-testing/blob/main/Sources/Testing/Testing.docc/MigratingFromXCTest.md#validate-asynchronous-behaviors). Для callback с результатом часто удобнее сначала сделать `async`-обёртку через [[1. Continuation|continuation]], а затем проверить возвращённые данные. Добавление случайной задержки в тест не задаёт момент завершения операции.

В основной пример мы не добавляли сеть и completion: сначала проверяется политика хранения. Число загрузок, отмена и одновременные запросы потребуют своих требований и управляемого источника данных.

### Вопросы на собеседовании

> [!faq]- Чем #expect отличается от #require?
> Неудачный `#expect` записывает ошибку проверки и позволяет идти дальше. `#require` бросает ошибку. С обычным `try` она прерывает текущую тестовую функцию; Optional-вариант при успехе возвращает развёрнутое значение.

> [!faq]- Что вернёт чтение a после записи a, записи b, чтения a и записи c при вместимости два?
> В нашем LRU вернутся данные `a`, а `b` будет удалён. FIFO удалит `a`, потому что не учитывает чтение. Если тесты проверяли только размер, они могли пропустить эту разницу.

> [!faq]- Почему первый красный запуск нужен до реализации?
> Он показывает, что проверка замечает конкретное отсутствующее поведение. Нужно увидеть ожидаемую причину падения: в нашем примере получен `nil` после записи. Ошибка сборки до запуска теста этого не подтверждает.

> [!faq]- Можно ли разделить один изменяемый кеш между всеми тестами?
> По умолчанию тесты могут идти параллельно. Изменения общего кеша сделают результаты зависимыми от соседних запусков. В примере каждый тест создаёт собственное значение `ImageCache`.

### Итог

- Контракт кеша определяет вместимость, поведение перезаписи и правило вытеснения до реализации.
- `#expect` позволяет продолжить проверку, а `try #require` подходит для результата, без которого следующие шаги теста бессмысленны.
- Параметризация проверяет несколько входов одной функцией, но сама по себе не добавляет новые свойства к проверке.
- Чтобы отличить FIFO от LRU, нужен сценарий с чтением перед переполнением.
- После зелёного запуска остаются проверка diff, чтение реализации и новые последовательности действий из исходного контракта.

### Практика

1. Напишите тест для перезаписи `a` перед добавлением `c`: после записей `a`, `b`, повторной записи `a` и записи `c` должны остаться новые данные `a` и данные `c`. Проверьте его сначала на FIFO, затем на LRU.
2. Замените короткие ключи в тестах на другие строки и переставьте значения байтов. Сохранятся ли результаты? Объясните, какие требования это проверяет и чего такая замена не доказывает.
3. Вернитесь к задаче 6 из [[1. Практический путь|практического пути]]. До изменения `ActivitiesStorage` запишите, сколько обращений к базе допускают два одновременных запроса одного ключа. Продумайте тест с управляемым завершением загрузки. В какой момент второй запрос сможет войти в актор, пока первый ждёт данные?

> [!success]- Подсказка к третьей задаче
> Между проверкой кеша и записью результата есть `await`. Пока первая загрузка приостановлена, другой запрос может увидеть тот же промах. Подмените базу источником, который считает обращения и завершается по сигналу теста. Заранее решите, требуется ли объединять одинаковые запросы: сам факт использования актора такого правила не задаёт. Механизм разобран в [[2. Actor Reentrancy]].
